# 와이퍼넷(WiperNet) 설계 문서

- 작성일: 2026-10-30
- 대상: 현대자동차그룹 차량용 앱 개발 공모전 (Pleos Connect, 1차 마감 2026-11-15 23:59)
- 상태: 사용자 승인 (2026-10-31). 같은 날 공모전 설명회와 Pleos 개발 문서를 확인하고 개정했다 (6.7장, 5.6장). 2026-11-02 구현 시작 전 결정을 6.9장에 더했다. 2026-11-04 시뮬레이터 설계 수정과 외부 자료(특보·재난문자·레이더) 연동을 6.10장에 더했다.
- 앱 이름: **와이퍼넷 (WiperNet)** (사용자 확정, 2026-11-02).

---

## 1. 의도와 이유

### 한 줄 요약
도로 위의 Pleos 현대차들이 와이퍼 작동 정보를 익명으로 모아서, 경로 앞 **지하차도·저지대의 침수 위험을 미리 경고하고 우회를 권하며**, 비 구간에 들어가기 전에 **차를 미리 준비시키는** 차량용 앱.

### 왜 이 아이디어인가
- 사용자는 "다른 현대차가 모은 정보를 다른 현대차가 쓰는 네트워크"에 끌렸다. 아이폰 '나의 찾기'처럼 기기가 많을수록 강해지는 구조다.
- 한국에서는 현대차그룹 차량 비중이 압도적이다. 2025년 내수 판매 기준 현대+기아 약 83.5%, 제네시스 포함 약 92% (딜사이트 집계 판매 대수로 계산). 같은 구조를 해외 브랜드가 하면 데이터가 듬성듬성하지만, 한국에서 현대차가 하면 촘촘해진다.
- 지하차도 침수는 한국에서 실제로 생명과 직결된 문제다.
  - 2023-07-15 오송 궁평2지하차도 침수 참사 (14명 사망).
  - 2022-08-08 서울 집중호우 (강남·동작 일대 침수).
  - 감사원(2024-06 보도): 전국 지하차도 1,086곳 중 182곳이 침수 우려가 크고, 132곳은 진입 차단시설이 없었다.
  - 서울시는 중점관리 지하차도 95곳 중 94곳에 진입차단시설을 설치했다. 하지만 차단시설은 **이미 물이 찬 뒤** 작동하는 마지막 방어선이다. 와이퍼넷은 그 전에, 운전자가 지하차도 쪽 경로를 고르기 전에 알려준다.

### 이미 있는 것과 차별점
| 기존 | 하는 일 | 와이퍼넷과의 차이 |
|---|---|---|
| 벤츠 Car-to-X (2016~ 상용) | 와이퍼를 **최고 단계**로 올리면 근처 벤츠에 "폭우" 경고 | 단일 경고만 한다. 지하차도 침수 판단이 없고 차를 준비시키지 않는다. 한국에서는 차량 밀도가 낮다 |
| INRIX Road Weather (2015~, 미국) | 커넥티드카 데이터와 기상 모델로 도로 기상 정보를 B2B로 판매 | 한국 서비스가 없다. 차량 제어 연동이 없다 |
| 도요타 × 웨더뉴스 (2019 시험) | 와이퍼 데이터로 강우 지도를 만들어 예보 개선 | 시험에 그쳤고 운전자 기능이 아니다 |
| 미시간대 연구 (2019 논문) | 차량 70대의 와이퍼가 레이더보다 정확함을 보임 | 연구 단계다 |
| 카카오내비 홍수 안내, 기상청 도로기상 | 공공 기상·홍수 정보를 내비에 표시 | 차가 직접 감지한 데이터가 아니다. 지하차도 단위의 실시간 판단이 없다 |
| 2017 현대차 해커톤 학생팀 | 수분 센서로 날씨 아이콘 변경 시연 | 와이퍼가 아니었고 출품작에 그쳤다 |

사용자와 합의한 솔직한 결론: "와이퍼로 비를 감지해 공유한다"는 개념 자체는 새롭지 않다(벤츠가 상용화했다). 차별점은 (1) **지하차도·저지대 침수 경고라는 한국형 생명안전 문제에 초점을 맞춘 것**, (2) **Pleos 차량 제어로 차를 미리 준비시키는 것**, (3) **한국 내 현대차 밀도에서 나오는 데이터 품질과 사업성**이다. 기획서는 이 차별점을 정면으로 내세우고, 벤츠 등 선행 사례를 숨기지 않는다.

## 2. 목표 / 비목표 / 반목표

### 목표 (사용자 기준)
1. 공모전 **수상**과 **포트폴리오**가 주 목적이다. 안드로이드 학습은 부차적이다.
2. 1차(11/15)에 **기획서 + 데모 영상(1~2분) + GitHub/APK**를 함께 낸다. 개발 결과물은 가점이 있고, 1차 통과(11/23) 후 2차 PT(12/3~4)까지 10일뿐이라 미리 만들어두는 게 안전하다.
3. 심사 기준 4개를 각각 명시적으로 채운다.
   - 차량 특화성: 와이퍼, 창문, 공조, 전조등, 내비 연동처럼 폰으로는 할 수 없는 기능을 쓴다.
   - 창의성: 지하차도 침수라는 구체적인 고통을 다루고, 차량 네트워크라는 해결 구조를 제시한다.
   - 기술 활용: Vehicle SDK, NaviHelper SDK, FusedLocation SDK, TextToSpeech SDK를 핵심 기능에 쓴다.
   - 사업성: 현대차 밀도에서 오는 네트워크 효과, B2G/B2B 데이터 사업.
4. 사용자의 관심사(회사에서 다루는 sim-to-real)를 살려서, **다수 차량 시뮬레이터로 전체 로직을 검증**하는 구조를 만든다. 이건 사용자가 매우 좋다고 한 부분이다.

### 비목표
- 실제 도로에서 배포하거나 실차로 검증하는 것.
- 기상학적으로 정확한 강우 예보 모델. 데모 수준의 합리적인 추정이면 된다.
- 안개(안개등), 급브레이크, 결빙 같은 다른 신호. 기획서에 "확장 계획"으로만 언급한다.
- 전국 단위 시뮬레이션. 데모는 서울 한 지역의 폭우 하루만 재현한다.
- 뉴스 연동. 보도는 사고 뒤에 나오고 위치가 넓어 운전 중 판단 근거로 약하다(사용자 결정, 2026-11-04). 데모용 과거 기록의 출처로만 쓴다(6.10).

### 반목표 (기술적으로 동작해도 실패로 보는 것)
- **운전 중 주의를 빼앗는 UI.** 운전 중에는 음성(TTS)과 한눈에 보이는 경고만 쓴다. 터치나 읽기가 많이 필요한 화면을 만들지 않는다.
- **잦은 오경보.** 한 대의 와이퍼만 보고 경고하면 "양치기 소년"이 된다. 여러 대가 동시에 감지할 때만 경고한다.
- **"벤츠 기능의 Pleos 복제판"으로 읽히는 것.** 경고 하나만 보여주는 데모는 실패다. 지하차도 시나리오와 차량 준비가 반드시 보여야 한다.
- **"공공 기상 정보를 다시 보여 주는 앱"으로 읽히는 것.** 외부 자료(특보·재난문자·레이더)가 주인공인 데모는 실패다. 데모의 첫 지하차도 경고는 와이퍼 신호에서 나와야 하고, 외부 자료는 확인과 보완으로 보인다(6.10).
- **개인 이동 경로가 드러나는 데이터 구조.** 같은 임시 ID로 이어지는 경로는 12~18분 조각까지만 생기고 2시간 뒤 지운다. 출발·도착 근처는 보내지 않는다(6.11).
- 검증 없이 정확도를 주장하는 것.

## 3. 제약

- **1인 참가.** 사용자는 안드로이드 경험이 사실상 없다. 코드는 Claude가 주로 쓰고, 사용자는 구조를 이해하고 2차 PT에서 직접 설명·시연할 수 있어야 한다.
- **시간:** 하루 1~4시간, 2026-10-30부터 11-15까지 약 30~40시간. 기획서 8~10시간, 나머지는 데모.
- **플랫폼:** Pleos Connect (안드로이드 기반 인포테인먼트). Android API 28+, Gradle 8.0+, Kotlin 또는 Java. 개발과 테스트는 Pleos 에뮬레이터에서 한다 (실차 없음).
- **사용자가 직접 해야 하는 일:** Pleos Playground 개발자 등록, Android Studio와 에뮬레이터 설치. 공모전 개발에는 SDK 접근 신청과 승인이 필요 없다 (6.7장).
- **개발 장비:** Apple M1, 메모리 16GB. Mac용(arm64) 에뮬레이터 이미지가 따로 있지만 문서의 그래픽 카드 요구 사양은 Windows 기준이라 실제로 띄워 봐야 한다. 같은 Mac에서 다른 업무용 Docker 컨테이너가 상시 돌고 있어, 에뮬레이터를 쓸 때는 잠시 멈추는 게 나을 수 있다.
- **플랫폼 정책:**
  - 앱은 차량 하드웨어나 센서에 직접 접근할 수 없다. Pleos Connect SDK의 API로만 접근한다. 카메라 API는 없다.
  - Vehicle SDK 권한은 앱마켓이 승인한 범위 안에서만 쓸 수 있다. 미승인 권한을 선언하면 심사에서 떨어진다. 이 심사는 실제 앱마켓 배포 때만 적용되고, 공모전 개발과 에뮬레이터 테스트는 매니페스트 선언만으로 된다 (6.7장).
  - 앱에 Distraction Optimization(DO)을 선언하지 않으면 기어 D에서 앱을 쓸 수 없다. DO를 선언한 앱도 `CarUxRestrictions`를 받아 제한 항목(키보드, 영상, 긴 글 등)을 직접 막아야 한다.
  - 화면에서 사라진 앱은 종료되지 않고 백그라운드에 남을 수 있다. 새로 실행된 앱은 주 화면(primary window)을 차지한다.
  - 성능 기준: 내비가 아닌 앱은 주행 중 CPU 5% 미만, 정차 중 25% 이하, RAM 400MB 이하. 백그라운드 폴링과 타이머는 최소화한다.
  - 운전 중 통신이 끊길 수 있다. 캐싱, 재시도, 오프라인 안내 UI를 권장한다.
  - NaviHelper 이벤트는 "내비 앱의 구현과 상태에 따라 달라질 수 있다". 에뮬레이터에서 실제로 오는지 일찍 확인해야 한다.
- **공모전 서류 규칙:** 02 작품 소개 부분에는 이름, 연락처, 소속을 쓰지 않는다. 양식에는 "공유 링크에도 개인정보·계정정보·개발자 실명이 노출되지 않도록 확인하세요"라는 안내가 있다(위반 시 불이익은 명시되지 않음). GitHub는 사용자 결정으로 개인 계정에 둔다(6.7).

### 확인된 SDK 기능 (2026-10-30 Pleos 문서 기준, 2026-10-31 보강)

- **SDK 버전 (2026-10-19 릴리즈):** Vehicle 2.3.2, NaviHelper 3.0.5, TextToSpeech 3.3.1, SpeechToText 3.3.1, FusedLocation 1.1.3. Maven 저장소 `https://nexus-playground.pleos.ai/repository/maven-releases/`, 좌표 `ai.pleos.playground:<SDK>:<버전>`.
- **퍼미션:** 와이퍼·창문 조회 `pleos.car.permission.CAR_WINDOWS`, 제어는 `CONTROL_CAR_*` 접두사(예: `CONTROL_CAR_WINDOWS`, `CONTROL_CAR_CLIMATE`, `CONTROL_CAR_LIGHTS`). 기어는 `CAR_DRIVE`. NaviHelper는 `NAVI_ROUTE`(정보 조회), `NAVI_ROUTE_SEARCH`(경로·경유지 요청). 위치 `FUSED_LOCATION`. 음성 `TTS_SERVICE`.
- **NaviHelper 3.0.5 변경:** 데이터 모델 생성자의 좌표 순서가 (위도, 경도)로 바뀌었다. `requestRouteWithWaypoints`가 생겼고 경유지는 최대 2개다. `initialize(onConnected, onFailed)`로 연결 결과를 받는다. 경로 탐색 완료는 `onRoutingCompleted`를 쓴다.
- **FusedLocation 1.1.3:** `isSupported()`로 지원 여부를 먼저 확인한다. 지정 영역 진입/이탈 알림 `addProximityAlert`가 생겼다(지하차도 접근 감지 후보).
- **TextToSpeech 3.3.1:** `ON_DEVICE` 모드는 네트워크와 앱 등록(Client ID)이 필요 없다. `HYBRID`/`SERVER` 모드는 My Project 자격 증명으로 앱 등록이 필요하다.
- **Virtual Console의 와이퍼 스위치는 Off, Auto, Low, High 네 값만 있다.** SDK 값(간헐 1~5, 연속 1~5)과 어떻게 대응하는지는 에뮬레이터에서 확인해야 한다. 위치를 바꾸는 카드는 없다. 기어(P/R/N/D), 창문 위치(0~100%), 에어컨, 디프로스터, 외부 조명 모드는 바꿀 수 있다.
- **LLM SDK는 종료됐다.** Gleo AI 연동은 Gleo Interface로 한다.
- **Wiper:** `getCurrentWiperSwitch` / `getCurrentWiperState`, 변경 리스너 `WiperStateListener`. 스위치 값은 `OFF`, `AUTO`, `MIST`, `INTERMITTENT_LEVEL_1~5`, `CONTINUOUS_LEVEL_1~5`, `SERVICE`, `OTHER`. 상태 값은 `ON`, `OFF`, `SERVICE`, `OTHER`.
- **Window:** 창문 제어와 상태.
- **HVAC:** `setHvacAc`, `setHvacDefroster`, `setHvacRecirculation`, `setHvacAutoRecirculation`, `setHvacFanSpeed`, `setHvacTemperature` 등.
- **Light:** `setLowBeamLightSwitch`, 안개등 스위치, 앰비언트 조명 등.
- **NaviHelper:** 목적지·경유지 설정, 경로 재탐색, `onTBTInfo` (안내 유형에 `TURN_ENTER_UNDER_*` 지하차도 진입, `TURN_TUNNEL` 포함, 남은 거리 포함), `onCurrentLocationInfo`, `onRouteStateInfo` (교통 상황 포함), `onCautionPointInfo`.
- **FusedLocation:** 차량 위치.
- **TextToSpeech / SpeechToText.**
- **Gleo AI 연동:** 앱이 함수를 등록하면 음성 비서가 호출하는 구조다. 필수는 아니고 선택 확장이다.

## 4. 사용자가 정한 방향 (정한 그대로)

1. **주제:** 와이퍼 데이터 기반 현대차 네트워크. "다른 현대차의 정보를 다른 현대차가 쓴다."
2. **기능의 중심:** **지하차도·저지대 침수 경고와 우회 권유**(1번)를 중심에 두고, **비 구간·더 강한 비 구간 진입 전 차량 준비**(2번)를 붙인다(사용자 결정 2026-11-10: 준비를 두 단계로 나눔. 와이퍼 지도는 이미 비가 내리는 곳을 보여 줄 뿐 예보가 아니라서, 비가 막 시작되거나 빠르게 몰려오는 곳은 미리 알 수 없다. 이미 내리는 비 구간으로 들어갈 때와 더 센 비 앞에서만 준비할 수 있다). **비 세기·이동 지도**(3번)는 가능하면 바탕 데이터와 보조 화면으로 활용한다.
3. **구성:** 세 부분으로 나눈다. 사용자가 "너무 좋다"고 했다.
   - **가상 차량 시뮬레이터:** 서울 지도 위 가상 현대차 수백 대가 실제 과거 집중호우 기록에 맞춰 와이퍼를 돌린다.
   - **서버:** 와이퍼 데이터를 모아 비 지도와 지하차도 침수 위험을 계산한다.
   - **차량 앱 (에뮬레이터 속 내 차):** 위험 정보를 받아 경고, 우회 권유, 차량 준비를 한다.
4. **1차 제출물:** 기획서 + 데모 영상 + GitHub/APK.
5. **데모 범위 축소:** 서울 한 지역의 폭우 하루, 차량 앱 기능은 3개(침수 경고, 우회 권유, 차량 준비)에 집중한다.
6. **SDK 승인이 늦어질 때의 대비:** 시뮬레이터 + 서버 + 앱 화면만으로도 영상을 만들 수 있게 한다.

## 5. 동작 설계 (Claude의 판단이 섞여 있으며 표시함)

### 5.1 차량 앱 — 데이터 보내기
- **언제 보내나 (사용자 결정, 2026-10-31):** 내비 길안내 중이거나 와이퍼가 켜져 있을 때만 보낸다. 둘 다 아니면 아무것도 보내지 않는다.
- 와이퍼 스위치/상태가 바뀔 때마다, 그리고 와이퍼가 켜져 있는 동안 주기적으로 (위치, 시각, 와이퍼 단계)를 서버로 보낸다.
- **길안내 중 와이퍼가 꺼진 차도 가끔 "꺼짐"을 보낸다 (Claude의 판단).** 비 오는 칸 근처의 "꺼짐" 보고가 있어야 와이퍼 고장·워셔액 같은 한 대짜리 오경보를 거를 수 있다(5.2의 중앙값 규칙). 격자 칸이 바뀔 때와 5분마다 보낸다.
- 와이퍼 단계를 0~1 강도 점수로 바꾼다. 예: 간헐 1~5 → 0.1~0.4, 연속 1~5 → 0.5~1.0, `MIST`는 제외 (Claude의 판단).
- **`AUTO` 모드 처리 (Claude의 판단, 미검증):** 자동 모드에서는 스위치가 `AUTO`로만 찍혀 세기를 알 수 없다. 상태(`ON`/`OFF`) 전환 빈도로 대략의 세기를 추정한다. 시뮬레이터는 차량의 일정 비율을 `AUTO` 모드로 설정해서 이 약점을 데모에서도 정직하게 다룬다.
- 통신이 끊기면 로컬에 쌓아두었다가 다시 보낸다.

### 5.2 서버 — 비 지도와 침수 위험
- 와이퍼 이벤트를 격자 칸(예: 500m) 단위로 집계해서 칸마다 "최근 10분 비 세기"와 "최근 1시간 누적"을 추정한다. 이게 3번 비 지도다.
- **오경보 방지:** 칸 안에서 서로 다른 차 N대 이상이 동시에 감지할 때만 비로 인정한다.
- **지하차도 침수 위험:** 각 지하차도 주변 칸들의 최근 세기와 누적량, 그리고 그 지하차도의 기본 위험도를 합쳐 단계(주의/경고/위험)를 매긴다. 지하차도 목록과 기본 위험도의 출처는 6장에 적은 대로 빌더가 결정한다.
- 차량 앱이 서버에 위험 정보를 가져가는 방식(주기적 조회/푸시)은 빌더가 정한다. 데모는 주기적 조회면 충분하다.
- **외부 자료 교차 확인 (사용자 결정, 2026-11-04):** 서버는 기상특보, 재난문자, 레이더를 함께 받아 와이퍼 판단과 합친다. 위험을 올리는 신호는 어느 출처든 받아들이고, 내리는 신호는 받지 않는다. 자세한 규칙은 6.10.
- **개인정보:** 차량 식별자는 일정 시간마다 바뀌는 임시 ID만 쓴다. 원본 이벤트는 짧게 보관하고, 집계된 칸 단위 값만 남긴다. 완전한 익명이 아니라 가명 수준이며, 한계와 보완은 6.11에 적는다.

### 5.3 차량 앱 — 운전자 기능
1. **침수 경고 + 우회 권유 (핵심):** 경로 앞에 위험 단계의 지하차도가 있으면 음성과 시스템 알림으로 알리고, 와이퍼넷 화면이 떠 있으면 큰 경고 띠도 보여 준다(5.6). 예: "1.2km 앞 ○○지하차도, 주변 차량들이 폭우를 감지했어요. 우회 경로를 안내할까요?" 운전자가 동의하면 NaviHelper로 경로를 바꾼다. 앞에 지하차도가 있다는 판단은 `onTBTInfo`의 지하차도 진입 안내와 지하차도 목록 위치 대조를 함께 쓴다.
2. **차량 준비:** 비 구간(10 mm/h 이상) 또는 더 강한 비 구간(30 mm/h 이상) 진입 1~3분 전, 창문이 열려 있으면 닫고, 김서림 방지(에어컨/디프로스터)를 켜고, 전조등을 켠다. 각 동작은 짧은 음성으로 알린다. 제어가 반영되지 않았거나 그 기능이 없으면 그 항목은 음성으로 권한다(6.5-2). 어디까지 자동으로 할지는 설정에서 고를 수 있다.
3. **비 지도 (보조):** 주차 중이거나 정차 중일 때 경로 위 비 세기와 위험 지하차도를 지도/띠로 보여준다. 운전 중에는 최소한으로만 보인다.

### 5.4 가상 차량 시뮬레이터 (sim-to-real)
- **목적:** (1) 실차 수백 대 없이 서버와 앱의 전체 로직을 검증한다. (2) 2차 PT에서 "그날 이 앱이 있었다면"을 재현한다.
- **재현 시나리오:** 2022-08-08 서울 집중호우, 강남·서초 일대 (Claude의 판단. 사용자는 "예를 들면 강남"이라는 제안에 동의했다).
- **입력:** 기상청 API허브의 방재기상관측(AWS) 매분자료(데모 지역 사방 약 8 km 안 관측소, `docs/setup-status.md`), 도로망 (예: OpenStreetMap).
- **동작:** 가상 차량 수백 대가 도로 위를 움직이고, 각 차는 자기 위치의 강수 세기에 맞춰 와이퍼 단계를 고른다. 사람마다 다르게 반응하도록 잡음을 섞고 일부는 `AUTO` 모드로 둔다. 실제 차량 앱과 **같은 서버 API**로 데이터를 보낸다.
- **에뮬레이터 속 내 차:** 같은 시나리오 안에서 지하차도 쪽 경로를 달리는 차 한 대로 등장한다. 내비로 목적지를 정해 길안내를 받으며 가는데, 그 경로가 그날 그 시각 강남 침수 지역의 지하차도를 지난다(사용자 결정, 2026-11-06. 실제 배포에서 앱이 쓰이는 모습과 같게). 에뮬레이터의 위치·내비를 시나리오에 맞춰 움직이는 방법은 빌더가 Pleos 에뮬레이터 기능을 보고 정한다. Virtual Console에는 위치를 바꾸는 기능이 없으므로(3장), 안드로이드 에뮬레이터 자체의 위치 기능이 Pleos 위치·내비에 반영되는지 먼저 확인하고, 안 되면 앱 안의 데모용 데이터 공급자를 쓴다.
- **시뮬레이터와 Virtual Console의 역할 (사용자 결정, 2026-10-31):** 시뮬레이터는 그대로 간다. Virtual Console은 에뮬레이터 속 차 **한 대**의 와이퍼·기어·창문·공조·조명을 손으로 바꾸는 도구라, "주변 차 여러 대가 동시에 감지"하는 상황을 만들 수 없다. 그래서 가상 차 수백 대는 시뮬레이터가, 내 차 조작은 Virtual Console이 맡는다.
- **검증:** 서버가 계산한 비 지도를 실제 AWS 관측값과 비교한 결과를 기획서와 PT에 숫자로 제시한다.

### 5.5 데모 영상 (1~2분) 흐름 (Claude의 제안)
1. 문제: 오송·강남 침수 장면 요약 자막 (5~10초).
2. 시뮬레이터: 강남 지도 위 가상 차량 수백 대, 비가 시작되면서 와이퍼 신호가 퍼지고 비 지도가 그려진다.
3. 지하차도 위험 단계가 "위험"으로 올라간다.
4. 에뮬레이터 속 내 차: 비 구간 진입 전 차량 준비 (창문, 김서림 방지, 전조등).
5. 경로 앞 지하차도 경고 → 음성 안내 → 우회 경로. 와이퍼 신호가 먼저 잡고, 호우경보 같은 외부 자료는 근거로 덧붙는다(6.10).
6. 마무리: "현대차가 많을수록 더 안전해지는 도로".

### 5.6 앱 동작 모델 (사용자 결정, 2026-10-31)

와이퍼넷은 사용자가 열어서 쓰는 앱이라기보다 **차량 기능처럼 뒤에서 도는 앱**이다. 애플 날씨의 "다음 1시간 강수 알림"처럼, 알림이 본체이고 앱 화면은 지금 상황을 보여 준다.

1. **처음 한 번 연다.** 설치 후 첫 실행에 동의 화면을 보여 주고 "동의" 버튼으로만 동의를 받는다.
2. **그 뒤로는 뒤에서 돈다.** 차가 켜지면 가벼운 감시 기능이 뒤에서 시작되고, 내비 길안내 시작이나 와이퍼 켜짐을 알아채면 본격적으로 움직인다(데이터 보내기는 5.1, 경고와 차량 준비는 5.3).
3. **경고는 음성과 시스템 알림으로만 한다.** 위험할 때 앱 화면을 강제로 띄우지 않는다. Pleos에서는 새로 뜬 앱이 주 화면을 차지해서 주행 중 내비를 밀어낼 수 있기 때문이다. 우회 질문은 음성과 알림의 "예 / 아니오" 버튼으로 받는다.
4. **앱을 열면 경로 앞 요약을 보여 준다.** 와이퍼넷이 잘 돌고 있는지, 경로 앞이나 주변의 비와 위험 지하차도를 한눈에 보여 준다. 사용자는 이 화면을 내비 옆 창에 띄워 두고 주행 중 흘끗 볼 수 있다. 주행 중에는 짧은 요약만, 정차·주차 중에는 비 지도까지 보여 준다. 설정은 화면 구석의 버튼으로 들어간다.
5. **Gleo 음성 질문은 확장이다.** "앞에 지하차도 괜찮아?"에 답하는 Gleo Interface 연동은 시간이 남으면 붙인다.

**이 모델을 고른 이유:** 참여하는 차 수가 곧 서비스 품질이다. 앱을 연 차만 데이터를 보내면 네트워크 효과가 무너진다. 그래서 뒤에서 도는 것은 꼭 필요하다. 비교한 대안은 (a) 매번 열어서 내비 옆에 두는 앱(참여 차량이 줄어 탈락), (b) 위험할 때 앱이 자동으로 뜨는 방식(내비를 가려 주의 분산, 심사 위험으로 탈락)이다.

**남은 위험:** 차가 켜질 때 Pleos가 앱을 뒤에서 자동으로 시작해 주는지는 문서에 없다. 에뮬레이터에서 일찍 확인한다. 안 되면 "처음 한 번 열면 그 뒤로는 계속 뒤에서 돈다"까지만 하고, 기획서에 한계로 적는다.

**선행 사례:** 2026-09 기준 Pleos App Market의 국내 앱 18종은 모두 직접 열어 쓰는 내비·음악·영상 앱이다. 뒤에서 지켜보다 알려 주는 외부 앱이나 안전 앱은 찾지 못했다(기존 11종의 전체 목록은 확인 못 함). 비슷한 "먼저 제안하기"는 차에 내장된 Gleo AI(출근 경로 선제 안내 등)에만 있다. 기획서 창의성 항목에서 "App Market 첫 백그라운드 안전 앱"으로 내세울 수 있다.

## 6. 빌더에게 맡기는 것

- 서버와 시뮬레이터의 언어와 프레임워크 (Claude의 기본안: Python + FastAPI 서버, 웹 지도 기반 시뮬레이터 시각화. 1인·단기 개발에 맞춘 선택이다).
- 격자 크기, N대 기준, 위험 단계 계산식, 와이퍼 단계 → 강도 매핑의 구체적 값.
- 지하차도 목록과 기본 위험도의 출처. 후보: 서울시 중점관리 지하차도 95곳, 서울시설공단 수방용 도로차단 설비 현황(공공데이터포털), OpenStreetMap의 지하차도. 데모는 강남 일대 몇 곳만 직접 정리해도 된다.
- 서버 배포 방식 (로컬 실행으로도 데모 가능).
- 에뮬레이터에서 NaviHelper 이벤트와 위치를 시나리오에 맞추는 방법. 안 되면 앱 안에 데모용 가짜 데이터 공급자를 둔다.
- 앱 화면의 시각 디자인 (Pleos 디자인 가이드를 따른다).
- 기획서 6번 항목(예상 MAU, 리텐션)의 추정 방법. Pleos 탑재 차종(더 뉴 그랜저 최초, 디 올 뉴 아반떼·신형 투싼 확대, 기아는 내년 확대 구상)과 판매량을 근거로 가정을 명시한다.

## 6.5 빌더 검토 후 정한 것 (Claude의 판단, 사용자가 읽고 바꿀 수 있음)

1. **검증이 자기 자신과 비교하는 구조가 되지 않게 한다.** 검증은 두 가지로 나누고, 각각이 무엇을 증명하는지 정직하게 밝힌다. (a) **재현 검증:** 서버가 잡음 섞인 와이퍼 신호만으로 시뮬레이터의 실제 강우장을 얼마나 복원하는지 (오차, 비 감지 적중률, 오경보율). 차량 밀도 두 가지(현재/미래)로 비교해서 네트워크 효과를 숫자로 보여준다. (b) **재현 데이터의 현실성:** 관측소를 하나씩 빼고 나머지로 만든 강우장 값을 뺀 관측소의 실제 값과 비교한다(leave-one-out). 데모 강우장은 관측소를 모두 쓴다. 강남·서초 관측소는 결과를 따로 적는다(사용자 결정, 2026-11-06. 30% 무작위 숨김은 강남 관측소가 데모에서 빠지거나 검증에서 빠져서 바꿨다). "와이퍼가 레이더보다 정확하다"는 주장은 시뮬레이션으로 증명할 수 없으므로, 미시간대 연구를 인용하는 데 그친다. 지하차도 위험 단계는 2022-08-08 강남·서초 일대 실제 통제·침수 기록을 찾으면 시각까지 비교한다. 못 찾으면 "예시 시나리오"라고 분명히 밝히고 정확도는 주장하지 않는다.
2. **차량 제어 권한 (2026-10-31 개정).** 공모전 개발에는 신청이 필요 없으므로 Window, HVAC, Light 제어 퍼미션을 매니페스트에 선언하고 실제로 제어한다. 차종에 그 기능이 없을 때(capability 없음)만 "창문을 닫아 주세요" 같은 음성 제안으로 바꾼다. 기획서에는 실제 앱마켓 배포 때 이 퍼미션을 앱마켓과 협의해야 한다고 적는다. **(2026-11-10 확인, 사용자 결정)** 에뮬레이터에서 Window·HVAC·Light set은 **Virtual Console이 브라우저에 열려 있을 때만** 반영된다. 닫혀 있으면 성공 콜백은 오지만 값이 바뀌지 않는다. Pleos 문서는 set의 실패만 `onFailed`로 알린다고 적고, 성공 콜백이 반영 완료라는 설명은 없다. 그래서 제어한 뒤 다시 읽거나 변경 이벤트로 반영을 확인하고, 반영되지 않은 항목만 음성으로 권한다(`docs/setup-status.md`). Playground에는 Vehicle Control 8개 항목이 "준비 중"으로 보여, 공개 시기와 써도 되는지는 공모전 사무국에 이메일로 문의한다.
3. **APK는 혼자서도 돌아가야 한다.** 심사위원이 APK를 설치했을 때 서버에 연결되지 않아도 되도록, 앱 안에 녹화된 시나리오를 재생하는 데모 모드를 넣는다.
4. **11/15에는 녹화·편집 영상이면 충분하다.** 시뮬레이터, 서버, 에뮬레이터가 한 시계로 맞춰 실시간 시연되는 건 2차 PT(12/3~4)까지 완성한다.
5. **차량 밀도는 두 가지로 보여준다.** 현재 수준의 Pleos 보급률과 기아까지 확대된 미래 보급률로 각각 돌려서, 차가 많아질수록 지도가 촘촘해지는 네트워크 효과를 정직하게 보여준다.
6. **저지대 도로는 데모에서 뺀다.** 데모는 지하차도만 다루고, 저지대는 확장 계획으로 언급한다.
7. 5장에서 "Claude의 판단"으로 표시한 항목(강남 2022-08-08 시나리오, AUTO 모드 추정, 데모 흐름)은 사용자가 바꾸지 않는 한 확정으로 본다.
8. **범위를 줄이지 않는다 (사용자 결정).** 자동 와이퍼 모드 세기 추정, 차 앱 비 지도 화면, 관측값 비교 검증, 에뮬레이터 실제 SDK 연동을 모두 넣는다. 일정이 밀리면 빼는 대신 사용자에게 먼저 알린다.

## 6.6 실제 차량 데이터 접근: 확인된 것과 미확인 (2026-10-30 Pleos 문서 기준)

- **확인됨:** Wiper 스위치·상태 조회 API와 변경 리스너가 있다. 위치 API가 있다. 앱은 화면에서 사라져도 종료되지 않고 백그라운드에 남을 수 있으며, 백그라운드에서 계속할 통신 작업은 실행 조건과 중단·재개 정책을 정의하면 된다. 차량 밖으로 나가는 텔레메트리는 차량 ID·사용자 ID의 익명화/가명화 정책을 세우라고 안내한다. 즉 이런 구조를 플랫폼이 예상하고 있다.
- **조건:** 앱 안에서 명확한 동의, 개인정보 처리방침 공개, 동의 철회 시 즉시 중단과 삭제가 필요하다. 위치정보를 저장·이용하는 앱은 서비스 국가 법령(한국: 위치정보법)을 따라야 하고, 앱마켓이 등록·신고 내역을 요구할 수 있다. 실제 출시 단계에서는 위치기반서비스사업 신고가 필요할 것으로 본다 (Claude의 판단, 법률 확인 필요).
- **미확인:** (1) Pleos가 이 앱에 Wiper·위치 권한을 승인할지, (2) 모든 Pleos 차종이 와이퍼 단계를 제공하는지 (capability 확인 필요, 일부 차종은 켜짐/꺼짐만 줄 수 있음), (3) 실차에서 장시간 백그라운드 동작이 어떻게 되는지. 실차 검증은 지금 할 수 없고, 공모전은 에뮬레이터가 기본 환경이다.
- **SDK 신청 상태 (2026-10-31 개정):** 공모전 설명회(2026-10-28)에서 공모전 개발 중에는 Vehicle, NaviHelper, TTS, STT, FusedLocation SDK를 승인 절차 없이 매니페스트 퍼미션 선언만으로 쓸 수 있다고 안내했다. 10/30에 적었던 "준비 중이라 신청 불가"와 그 대비책(위치는 NaviHelper로, 음성은 안드로이드 TTS로, 차량 제어는 음성 제안으로 대신)은 **쓰지 않는다 (사용자 결정).** 위치는 FusedLocation, 음성은 Pleos TTS(`ON_DEVICE` 모드), 차량 준비는 Vehicle SDK 제어를 쓴다. 남는 대비는 두 가지뿐이다: 그 차종에 기능이 없을 때(capability, `isSupported()`)와, 에뮬레이터에서 실제로 동작하지 않는 것이 확인됐을 때. **2026-11-10 에뮬레이터 확인:** Playground 프로젝트에서는 FusedLocation·TTS·STT·Vehicle Control이 "준비 중"으로 보이지만, FusedLocation, TTS(`ON_DEVICE`), STT(`ON_DEVICE`, 한국어 인식까지)가 동작한다. Vehicle Control은 Virtual Console이 브라우저에 열려 있을 때만 반영된다(6.5-2).
- **개발 중 데이터:** 에뮬레이터의 Virtual Console(브라우저 화면)에서 와이퍼, 창문, 조명, 공조 값을 직접 바꿀 수 있다. 앱 코드는 실제 SDK를 호출하고, 값만 가상이다. 문서에 위치 조작 방법은 없다.
- **조치:** SDK 접근 신청은 하지 않는다. 외부 API와 퍼블릭 네트워크 연결은 설명회에서 가능하다고 확인했으므로 서버 전송 자체는 문제없다. 실차의 와이퍼 권한 승인 여부와 차종별 와이퍼 단계 제공 여부는 공모전 범위 밖이라, 기획서에 "배포 시 확인할 사항"으로 적는다.

## 6.8 개정 후 빌더 검토에서 정한 것 (2026-10-31, Claude의 판단, 사용자가 읽고 바꿀 수 있음)

1. **심사위원이 보는 것과 서버 위치.** 심사위원이 APK만 설치하면 앱 안의 녹화 시나리오 재생(데모 모드)만 본다. 실시간 서버·시뮬레이터·에뮬레이터 연동은 사용자의 Mac에서 로컬로 돌려 영상과 2차 PT에서 보여 준다. 외부 서버 호스팅은 하지 않는다. 앱은 데이터 공급원을 두 가지(데모 재생, 라이브 서버)로 둔다.
2. **에뮬레이터 속 내 차의 위치와 경로.** 첫 번째 개발 작업으로, 에뮬레이터에서 (a) 안드로이드 에뮬레이터의 위치 기능이 FusedLocation에 반영되는지, (b) NaviHelper `onTBTInfo`·`onCurrentLocationInfo`가 실제로 오는지, (c) 차가 켜질 때 앱이 뒤에서 자동 시작되는지, (d) Virtual Console 와이퍼 Low/High가 SDK에서 어떤 값으로 오는지를 짧게 확인한다. 위치나 TBT가 안 오면 데모용 데이터 공급자가 위치·TBT·기어·와이퍼를 **한 인터페이스 뒤에서 함께** 대신한다(기존 계획의 Replay 방식). 와이퍼·창문·공조·조명은 가능한 한 실제 SDK를 쓴다.
3. **자동 시작이 안 될 때.** 첫 실행 이후 포그라운드 서비스로 계속 돈다. 구체적인 서비스 형태는 빌더가 정한다.
4. **경고와 응답 방식.** Pleos 시스템 알림은 액션 버튼을 지원한다(디자인 가이드 System Notification). 우회 질문은 음성 안내 + 알림의 "예 / 아니오" 버튼으로 받고, STT로 "네/아니오" 음성 응답도 받는다. 알림 버튼이 에뮬레이터에서 동작하지 않으면 음성 응답만으로 한다.
5. **와이퍼 Low/High 대응.** 서버는 원시 스위치 값을 받아 세기로 바꾼다(5.2). 에뮬레이터에서 Low/High가 SDK의 연속 단계 값으로 오면 기존 표를 그대로 쓰고, 다른 값으로 오면 서버 변환표에 그 값을 추가한다.
6. **익명 ID와 보관 기간.** 차량 임시 ID는 12~18분 사이 무작위 간격으로 바꾸고(처음에는 15분 고정이었다, 6.11), 서버는 원시 이벤트를 2시간까지만 보관한다(구현 계획의 전역 제약과 같다).
7. **일정이 밀릴 때.** 6.5-8대로 기능을 빼지 않고 먼저 사용자에게 알린다. 11/15 영상은 녹화·편집본이면 된다(6.5-4).

## 6.9 구현 시작 전 결정 (사용자 결정, 2026-11-02)

1. **앱 이름은 "와이퍼넷 (WiperNet)"으로 확정한다.**
2. **서버는 메모리에만 저장한다. DB와 Alembic은 지금 넣지 않는다.**
   - 이유: 2차 PT 조건은 "PT 심사 전까지 실제 동작 가능한 앱 개발을 완료"이고, App Market 출시는 요구하지 않는다. PT 시연도 2022-08-08 강남 시나리오를 사용자의 Mac에서 시뮬레이터, 서버, 에뮬레이터로 실시간으로 돌린다. "실제 동작"은 앱이 실제 SDK를 호출하고 실제 HTTP 서버와 통신한다는 뜻이며, DB가 필요하지 않다. App Market 탑재 준비 지원은 수상 혜택이고, 공모전 안내에도 "최종 입점 또는 배포를 보장하지 않습니다"라고 적혀 있다.
   - DB가 필요해지는 때: 수상 후 실제 운영(2027-02 이후)을 준비할 때다. 그때 바꾸기 쉽도록 저장 코드는 `store.py` 경계 뒤에 둔다.
   - 2차 심사 기준은 아직 공개되지 않았다. 공개된 기준이 운영 준비도를 본다면, 1차 결과 발표(11/23)부터 PT 사이에 SQLite + Alembic을 넣을지 다시 정한다.
3. **브랜치와 PR.** 1인 개발이지만 `main`은 항상 제출할 수 있는 상태로 두고, 계획의 Task마다 브랜치(`{type}/task-{NN}-{요약}`)를 따서 GitHub PR로 합친다. dev 브랜치는 두지 않는다(스테이징 서버가 없다). 제출 시점에는 `round1-submit`, `round2-pt` 태그를 단다. 자세한 규칙은 `CLAUDE.md` 5장에 있다.
4. **기능지도.** `docs/features/README.md`에 기능별 상태, 코드 위치, 테스트, 에뮬레이터 확인 결과, 의존 관계를 적는다. 에이전트는 구현 전에 읽고, 구현 후 같은 PR에서 고친다.
5. **저장소를 새로 만들었다.** 기존 이력에 설계 문서 커밋이 `feat` 브랜치에 섞여 있어서, 사용자가 GitHub 저장소를 지우고 같은 이름으로 다시 만들었다. 첫 커밋은 설계와 계획 문서다.

## 6.10 시뮬레이터 설계 수정과 외부 자료 연동 (2026-11-04)

계획을 시뮬레이터·서버·앱이 만나는 곳 중심으로 다시 읽고 찾은 문제와, 그 해결로 정한 것을 적는다. 사용자가 해결 방향을 확정했다. 수치(비율, 시간)는 Claude의 판단이며 가정치로 표시한다.

### 6.10.1 시뮬레이터·서버 수정

1. **시계를 하나로 맞춘다.** 서버 시계는 받은 이벤트의 최대 시각이다. 라이브 모드 앱은 자기 기기 시각이 아니라 **서버에서 마지막으로 받은 `/v1/clock` 값**을 이벤트 시각으로 쓴다. 서버 시계가 아직 없으면(`null`) 보내지 않는다. 그래서 앱이 2026년 시각으로 서버 시계를 밀어 2022년 데이터를 지우는 일이 없다.
2. **시뮬레이터 속도를 구간별로 바꾼다.** 비가 퍼지는 장면은 빠르게(기본 60배속), 에뮬레이터 속 내 차가 달리는 장면은 실제 속도로 보여 주도록 `--slow-from 시각 --slow-speed 배속` 옵션을 둔다.
3. **시뮬레이터는 시작할 때 서버를 초기화한다**(`POST /v1/reset`). 다시 돌릴 때 이전 실행의 늦은 시계가 남아 새 이벤트가 화면에 안 나오고 바로 지워지는 문제를 막는다.
4. **시뮬레이터도 앱과 같은 업로드 규칙을 쓴다.** 차마다 길안내 중 여부를 정하고(가정치 40%), 길안내 중인 꺼진 차는 칸이 바뀔 때와 5분마다 "꺼짐"을 보낸다. Python과 Kotlin에 같은 판정 사례를 테스트로 넣어 두 구현이 어긋나지 않게 한다.
5. **고장 차를 넣는다.** 비와 상관없이 와이퍼가 연속 5단으로 도는 차를 1% 둔다(가정치). 검증에서 이 차들이 비 칸을 만들지 않는지 보인다.
6. **약한 비에서는 와이퍼를 끈다.** 역거리가중 강우장은 관측소 하나만 비가 와도 지역 전체가 0보다 커진다. 운전자 규칙은 0.5 mm/h 미만이면 꺼짐이다.
7. **자동(AUTO) 와이퍼는 켜짐·꺼짐을 하나하나 보내지 않는다.** 앱과 시뮬레이터가 최근 60초 와이퍼 횟수(`auto_wpm`, 계속 켜져 있으면 40)를 직접 세서 60초마다 보낸다. 서버는 상태 이력을 모으지 않고 이 숫자로 세기를 계산한다. 약한 비에서 차 한 대가 분당 80건을 보내던 통신량 문제가 사라진다. AUTO에서 와이퍼 한 번마다 상태가 바뀌는지는 에뮬레이터에서 확인한다(미검증).
8. **뷰어는 최근 5분 안에 보낸 차만 그린다.** 임시 ID가 바뀌면서 옛 ID 점이 지도에 쌓이는 것을 막는다.
9. **차량 무리 실행을 한 곳에 둔다.** `fleet.py`가 시간별 이벤트 묶음을 만들고, 실행기(서버로 전송), 검증, 데모 내보내기가 모두 이것을 쓴다.
10. **검증 지표를 정직하게 바꾼다.** 적중률은 실제 비가 온 모든 칸을 분모로 한다(결과가 없는 칸은 놓친 칸). 오차는 실제 비가 60 mm/h 이하인 칸과 넘는 칸을 나눠 보인다. 임시 ID 회전 때문에 한 차가 두 대로 세진 비율도 적는다(익명성 때문에 구조는 그대로 둔다).
11. **데모 시나리오는 "차량 준비 → 지하차도 경고" 순서가 나오는 구간을 고른다.** 비 구간에 먼저 들어가니 준비가 먼저다(설계 5.5의 장면 순서도 이에 맞춘다). 찾는 시간대를 17~21시로 넓힌다.
12. 실행기는 강우장과 도로망을 인자로 받아 작은 가짜 데이터로 테스트한다. 도로망은 서로 오갈 수 있는 가장 큰 덩어리만 남긴다.
13. **같은 지하차도 경고 쿨다운(300초)은 단계가 오르면 무시한다.** 호우특보로 "주의" 안내를 한 뒤 몇 분 안에 차량 근거 "경고"가 와도 막히지 않는다. 그래서 데모의 첫 *경고*(WARNING 이상)는 와이퍼 신호에서 나오고, 그 전의 특보 안내는 "서울 전역" 수준의 배경으로 보인다. **(2026-11-10 개정, 사용자 결정)** 쿨다운은 WARNING 이상에만 둔다. 호우경보는 몇 시간씩 이어지므로 CAUTION 안내는 지하차도에 한 번 다가갈 때 한 번만 하고, 운전자가 "그만"이라고 하면 주차(기어 P)할 때까지 CAUTION 안내를 끈다. 운전 중에는 화면을 만질 수 없어 음성으로 끈다. WARNING 이상은 끌 수 없다. 차량 준비도 같은 방식으로, 10분에 한 번이지만 "곧 더 강한 비"는 10분 안이어도 바로 알린다.
14. **데모 모드의 우회.** 운전자가 "예"라고 하면 데모 재생은 미리 내보낸 우회 경로로 갈아탄다. 데모 모드는 NaviHelper를 부르지 않는다.
15. **라이브 모드는 시뮬레이터와 함께만 돈다(공모전 범위).** 서버 시계는 시뮬레이터 이벤트로 움직인다. 실제 차만 있는 운영에서는 서버가 실제 시각을 시계로 쓰도록 바꾼다. 라이브 시연의 느린 구간 시작은 데모 시나리오가 고른 구간과 같게 한다.

### 6.10.2 와이퍼의 한계: 60 mm/h 포화

- 연속 5단은 60 mm/h로 바뀐다. 운전자가 최고 단계로 돌리면 비가 더 와도 신호가 같으므로, 와이퍼만으로는 시간당 80과 100을 구분할 수 없다. 1시간 누적도 최대 60 mm에서 멈춘다. 이건 변환표의 버그가 아니라 신호 자체의 한계다.
- **포화 칸:** 칸의 차 절반 이상이 수동 연속 5단일 때 그 10분 구간을 포화로 본다. AUTO 계속 켜짐은 12 mm/h부터 같은 신호라 포화로 세지 않는다(약 44 mm/h로 계산된다). 연속 포화 시간을 `saturated_min`으로 낸다.
- 포화 칸의 중앙값은 이미 60 mm/h라 위험 단계 기준(60, 위험도 높은 곳 45)에 닿는다. 그래서 포화 규칙은 단계를 따로 올리지 않고 두 가지에 쓴다. (1) **레이더 대체:** 포화 구간은 그 칸의 레이더 값이 더 크면 레이더 값을 세기와 누적에 쓴다. 그러면 60을 넘는 비와 누적이 보인다. (2) **안내 근거:** 30분 넘게 포화면 "와이퍼로 잴 수 있는 한계를 넘는 비가 30분째"라는 근거를 붙인다.
- 지하차도 단계 기준(20/40/60 mm/h, 30/50/80 mm)은 바꾸지 않는다. 레이더 대체로 누적 기준에 닿을 수 있다. 레이더가 없을 때 누적 "위험"(80 mm)은 닿지 않지만, 세기 기준(60)으로 위험 단계는 나온다. 이 한계는 기획서에 적는다.

### 6.10.4 와이퍼와 외부 자료가 어긋날 때 (사용자 결정, 2026-11-04)

**원칙: 위험을 올리는 신호는 어느 출처든 받아들이고, 위험을 내리는 신호는 받지 않는다.** 외부가 조용하다고 와이퍼 경고를 낮추지 않고, 와이퍼가 조용하다고 공식 경고를 무시하지 않는다. 운전자 안전에서는 한 번 놓치는 비용이 한 번 헛경고하는 비용보다 훨씬 크다. 최종 단계는 출처별 단계의 최댓값이다.

| 출처 | 낼 수 있는 단계 | 이유 |
|---|---|---|
| 와이퍼 (3대 합의) | NONE~DANGER (기존 기준) | 도로 위, 지금, 칸 단위. 와이퍼넷의 본체 |
| 와이퍼 포화 + 레이더 | 포화 구간의 세기·누적에 레이더 값을 넣어 같은 기준으로 계산 | 와이퍼가 못 재는 60 이상을 레이더가 채운다 |
| 레이더만 (차가 없거나 레이더가 더 셈) | 같은 기준, 최대 WARNING | 정량적이지만 5~10분 늦고 하늘에서 잰다 |
| 호우주의보·경보 (지하차도의 특보 구역) | 최대 CAUTION | 구·시 단위로 넓다 |
| 재난문자: 지하차도 이름 + 통제·침수 | DANGER | 공식 통제다 |
| 재난문자: 그 구 또는 시 전체("서울특별시")의 호우 안내 | 최대 CAUTION | 넓은 지역 안내다 |

- 서버는 단계와 함께 **근거 목록**(`reasons`: `vehicles`, `saturated`, `radar`, `kma_warning`, `alert_closure`, `alert_rain`)을 돌려준다. 앱은 근거에 맞는 고정 문구를 덧붙인다. 예: "주변 차량들이 폭우를 감지했어요. 호우특보도 발효 중이에요."
- "3대 이상" 규칙은 그대로다. 외부 자료가 있어도 차 한 대짜리 와이퍼 신호는 쓰지 않는다.

## 6.11 익명성의 한계와 보완 (사용자 결정, 2026-11-08)

| 유럽 C-ITS(차량 간 통신) | 가명 인증서를 고정값 + 무작위 시점에 바꿈(예: 800 m 이상 + 2~6분). 바꿀 때 잠깐 안 보내는 방법도 연구됨. 가명 교체만으로는 추적을 완전히 막지 못한다는 연구가 많다 | ID 교체 시점을 무작위로 한다(아래) |
| 벤츠 Car-to-X | 동의한 차만, 서버에서 바로 가명 처리, 몇 주 뒤 삭제 | 동의(A1)는 같다. 보관은 2시간으로 더 짧다 |

**보완**
1. **ID 교체 시점 무작위:** 15분 고정 대신 12~18분 사이 무작위. 시뮬레이터(S5)는 Task 8에서 반영했고, 앱 `TempId`(A5)는 Task 13에서 한다.
2. **출발·도착 근처 안 보내기:** 길안내 출발 뒤 처음 300 m와 목적지 300 m 안에서는 보내지 않는다. 집·회사 위치를 감추는 가장 중요한 장치다. 앱 업로드 규칙(A16, Task 15)에서 하고, 같은 사례를 C5에 넣어 시뮬레이터도 맞춘다.
3. **배포 서버에서 뷰어용 차량 조회(`/v1/debug/vehicles`)를 끈다.** 차 한 대씩 위치를 내보내기 때문이다. 데모·개발에서만 쓴다.
4. **검토만:** 위치 대신 격자 칸 번호(약 500 m)만 보내는 방법. 지하차도 판단, 업로드 규칙, API 계약이 함께 바뀌어 공모전 범위에서는 하지 않는다.
